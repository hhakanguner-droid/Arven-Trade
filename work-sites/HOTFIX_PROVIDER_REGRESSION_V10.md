# ARVEN Trade — Sites Version 10 Provider Regression Hotfix

## Incident

Live Sites Version 10 deployed with SHA `397f265123856379e6a25a8b412778a655e6de71` introduced a production regression after the Phase 14 stale-job/progress hotfix.

Observed live behavior on 2026-08-27:

- Ticker: `ARTMS`
- Job reaches real progress start at `Piyasa Analisti`
- Progress: `%1`
- All remaining agents stay waiting
- Job terminates as `failed`
- Error type reported by Sites deployment smoke/user flow: `ProviderOutputInvalid`

The stale-job/progress observability work was intended to be orthogonal to provider/model/output semantics. It must not make an analysis fail that the pre-Version-10 execution path would have accepted.

## Required correction

Use **Sites Version 9 analysis execution/provider semantics as the behavioral baseline** and **Version 10 progress/stale-job protections as the observability/safety layer**.

The fix must be surgical:

### Preserve from Version 10

- additive D1 progress fields
- `analysis_progress_events`
- real server-side agent progress events
- nine ARVEN agent status UI
- heartbeat/progress separation
- progress-stall timeout (`AnalysisStalled`)
- hard timeout (`AnalysisTimeout`)
- late-write protection
- terminal-job no-requeue protection
- polling stop on terminal state

### Restore from Version 9

Diff Version 10 against Version 9 and restore the exact pre-hotfix behavior for all code affecting:

- provider/model request construction
- provider credentials/model selection
- tool invocation semantics
- response parsing
- output acceptance/normalization
- quality/validation gates
- provider exception mapping
- final analysis result assembly

Do **not** introduce or tighten a provider-output quality contract as part of the progress hotfix. If Version 9 accepted a provider response, Version 10/next version must accept the same response unless the provider itself returned a genuine hard error.

`ProviderOutputInvalid` must not be generated by a new validator added incidentally during this hotfix. If the error type already existed before Version 10, prove that the exact same input would have failed on Version 9 before retaining it.

## Progress instrumentation isolation

Progress telemetry must be side-effect-only and fail-open relative to the analysis engine:

- progress event write failure must not fail the analysis
- heartbeat write failure must not alter provider output validation
- current-agent/status rendering must not modify prompts, messages, tool results, or model responses
- progress callbacks/hooks must not consume, transform, replace, truncate, sanitize, or validate provider output
- timeout watchdog may terminate only when configured timeout/stall conditions are actually met

The analysis engine must remain functionally identical to Version 9 except for explicit timeout/cancellation boundaries.

## Regression test: ARTMS

After the correction, run a real production smoke with `ARTMS`.

Required evidence:

1. Job transitions `queued -> running`.
2. `Piyasa Analisti` starts with a real server-side event.
3. The job advances beyond the first agent. At least the next genuine agent/stage must be observed.
4. No immediate `ProviderOutputInvalid` is introduced by the progress layer.
5. Preferably the full nine-agent flow completes and job becomes `succeeded`.
6. If the real provider returns a genuine independent error, report the raw safe error type/message and prove it is unrelated to progress instrumentation.

Also run one previously known BIST ticker (`GARAN` or `THYAO`) to rule out ticker-specific behavior.

## Safety regression tests

Re-run and keep passing:

- `AnalysisStalled`
- `AnalysisTimeout`
- late-write cannot change terminal record
- terminal failed/succeeded job is not requeued
- no maintenance/debug endpoint remains
- history/watchlist/KAP records unaffected

## Fallback if surgical diff is uncertain

If the exact regression cannot be isolated confidently:

1. Roll back the live execution/provider path to Sites Version 9.
2. Reapply only the minimal progress persistence/UI hooks around it.
3. Do not carry over any Version 10 output validator/provider parsing change.
4. Re-run all progress and timeout tests before publishing.

Availability of a truthful progress display is secondary to preserving a working analysis engine.
